# 11. 네트워크 · 멀티플레이

> 클라이언트 예측 · 서버 재조정 · 보간 · 롤백 넷코드 · 락스텝 · 델타 압축 · AoI

멀티플레이의 모든 기법은 하나의 문제에서 출발합니다: **광속은 유한하고 패킷은 유실된다.**

---

## 0. 두 가지 근본 모델

| 모델 | 동기화 대상 | 특징 | 장르 |
|---|---|---|---|
| **상태 동기화 (State Sync)** | 월드 상태 (위치, HP) | 서버 권위, 치팅에 강함, 대역폭 ∝ 객체 수 | FPS, MMO |
| **입력 동기화 (Lockstep)** | 입력만 | 대역폭 ∝ 플레이어 수 (객체 수 무관), **완전 결정론 필수** | RTS, 격투 |

---

## 1. 클라이언트 사이드 예측 (Client-Side Prediction)

입력 후 서버 응답을 기다리면 100ms 지연이 체감됩니다. 그래서 **클라이언트가 먼저 움직입니다.**

```
1. 입력에 시퀀스 번호를 붙여 서버로 전송하고, 입력을 링 버퍼에 저장
2. 동시에 로컬에서 즉시 시뮬레이션 (예측)
3. 서버는 권위 있는 결과를 시퀀스 번호와 함께 회신
4. 클라이언트는 그 시점의 자기 예측과 서버 결과를 비교
```

---

## 2. 서버 재조정 (Server Reconciliation)

예측이 틀렸을 때의 복구 절차입니다.

```
서버 응답: "시퀀스 #42 시점의 너의 위치는 (10, 0, 5)"

1. 로컬 상태를 서버가 알려준 #42 상태로 되감기(rewind)
2. 링 버퍼에 저장해둔 #43 ~ #50 입력을 다시 순서대로 시뮬레이션(replay)
3. 결과를 현재 상태로 채택
→ 입력 8개를 한 프레임에 재적용하므로 유저에게는 거의 안 보임
```

**여기서 링 버퍼(01번 문서)가 필수**입니다. 입력 히스토리와 상태 스냅샷을 고정 메모리로 유지합니다.

### 부드러운 보정
위치를 즉시 순간이동시키면 튑니다. 오차가 작으면 **여러 프레임에 걸쳐 스무딩**하고,
임계값을 넘는 큰 오차만 즉시 스냅합니다.

---

## 3. 엔티티 보간 (Entity Interpolation)

**다른** 플레이어는 예측하지 않습니다(입력을 모르므로). 대신 과거를 보여줍니다.

```
수신 스냅샷:  t=100ms    t=150ms    t=200ms
렌더 시점:            t=175ms  ← 의도적으로 100~200ms 뒤처져 렌더
                      두 스냅샷 사이를 보간 → 완전히 부드러움
```

- **보간 버퍼**를 두는 대가로 타 플레이어가 약간 과거에 보입니다
- 패킷이 늦거나 유실되면 **외삽(Extrapolation / Dead Reckoning)** 으로 속도 기반 추측.
  단, 외삽은 틀릴 확률이 높아 짧게만 사용합니다

---

## 4. 지연 보상 (Lag Compensation)

"분명 머리를 맞췄는데 안 맞았다" 문제.

```
클라이언트는 200ms 과거의 적을 보고 쏨
→ 서버는 사격 시각을 역산해 히트박스를 그 시점으로 되감아 판정
→ 쏜 사람 기준으로 맞은 것을 인정
```

### 트레이드오프
맞은 쪽 입장에서는 "엄폐물 뒤로 숨었는데 죽었다"가 발생합니다.
쏜 사람과 맞은 사람 중 **누구의 체감을 우선할지는 게임 디자인 결정**입니다. 보통 슈터는 쏜 사람을 우선합니다.

---

## 5. 롤백 넷코드 (Rollback / GGPO)

격투 게임의 표준. 프레임 단위 정확도가 생명인 장르입니다.

```
1. 상대 입력이 아직 안 왔으면 "직전 입력을 반복할 것"으로 예측하고 진행
2. 실제 입력이 도착했을 때 예측과 다르면
   → 그 프레임의 저장된 상태로 롤백
   → 올바른 입력으로 현재 프레임까지 고속 재시뮬레이션
3. 렌더는 항상 최신 결과만 표시
```

### 요구 조건
- **완전 결정론** — 같은 입력 → 반드시 같은 결과
- **빠른 상태 저장/복원** — 프레임당 수 회 가능해야 함 (상태를 POD 구조체로 설계)
- 부동소수점 대신 **고정소수점** 또는 플랫폼 간 일관된 연산
- `Dictionary` 순회 순서, `UnityEngine.Random` 전역 상태, `Time.deltaTime` 의존 — **전부 결정론을 깨는 요인**

### 지연 기반(Delay-based)과의 비교
| | 지연 기반 | 롤백 |
|---|---|---|
| 방식 | 입력을 n프레임 늦춰 동기화 | 예측 후 틀리면 되감기 |
| 체감 | 입력 지연이 상시 존재 | 입력은 즉시, 가끔 화면이 튐 |
| 구현 | 쉬움 | 어려움 (결정론 + 상태 직렬화) |

## 6. 락스텝 (Deterministic Lockstep)

모든 클라이언트가 **같은 입력으로 같은 시뮬레이션**을 독립 실행합니다.

### 장점
- 유닛이 수천 개여도 **전송량은 플레이어 입력뿐** → RTS에 최적
- 리플레이가 입력 로그만으로 재현됨 (용량 극소)

### 단점
- 완전 결정론 필수 (롤백과 동일한 제약)
- **한 명이 느리면 전원이 대기** (턴 지연)
- 데스싱크(desync) 디버깅이 매우 어려움 → 주기적 체크섬 비교 필수

---

## 7. 대역폭 최적화

| 기법 | 설명 |
|---|---|
| **델타 압축** | 변경된 필드만 전송. 이전 스냅샷 대비 diff |
| **양자화 (Quantization)** | float 위치를 16bit 고정소수점으로. 회전은 쿼터니언 smallest-three(3개만 전송) |
| **비트 패킹** | 버튼 8개 = 1바이트, 열거형은 필요한 비트 수만 |
| **관심 영역 (AoI)** | 주변 것만 동기화. **그리드/쿼드트리**로 관리 (02·03번 문서) |
| **갱신 빈도 차등** | 가까운 적은 30Hz, 먼 적은 5Hz |
| **우선순위 기반 전송** | 대역폭 예산 내에서 중요한 엔티티부터 (우선순위 큐) |
| **신뢰성 선택** | 위치는 UDP 비신뢰(최신값이 중요), 아이템 획득은 신뢰 전송 |

### AoI가 MMO에서 핵심인 이유
```
1000명 접속 × 서로에게 전송 = 100만 쌍
AoI로 시야 50m 내 평균 20명만 → 2만 쌍  (50배 절감)
```

---

## 8. 서버 권위와 치팅 방지

- **클라이언트는 절대 신뢰하지 않는다** — 데미지, 아이템 획득, 이동 가능 여부는 서버가 판정
- 클라이언트가 보내는 것은 **입력 또는 의도**여야 함 ("나는 20 데미지를 줬다"가 아니라 "나는 공격 버튼을 눌렀다")
- 이동 속도 검증(speed hack), 사거리 검증, 쿨다운 검증
- 클라이언트 예측은 **UX용 낙관적 표시**일 뿐, 권위는 항상 서버

---

## 9. 학습 순서 제안

```
1. UDP/TCP 차이와 왜 게임이 UDP를 쓰는지
2. 상태 동기화 vs 입력 동기화
3. 클라이언트 예측 + 서버 재조정 (직접 구현해볼 것)
4. 엔티티 보간
5. 지연 보상
6. 결정론 시뮬레이션 → 롤백 / 락스텝
7. 대역폭 최적화 (델타, 양자화, AoI)
```

> 필독 자료: Gabriel Gambetta "Fast-Paced Multiplayer" 시리즈, Valve의 Source Multiplayer Networking 문서, GDC의 GGPO 발표.

## 체크리스트

- [ ] 상태 동기화와 입력 동기화의 차이와 각각 맞는 장르를 설명할 수 있다
- [ ] 클라이언트 예측 + 서버 재조정 흐름을 시퀀스 번호와 링 버퍼를 포함해 설명할 수 있다
- [ ] 타 플레이어를 왜 과거 시점으로 보간해 렌더하는지 안다
- [ ] 지연 보상이 "엄폐물 뒤에서 죽는" 문제를 만드는 이유를 설명할 수 있다
- [ ] 롤백 넷코드가 요구하는 결정론 조건과, 그걸 깨는 코드 패턴을 나열할 수 있다
- [ ] AoI가 MMO에서 왜 필수인지 수치로 설명할 수 있다
- [ ] 클라이언트가 서버에 "데미지"가 아니라 "입력"을 보내야 하는 이유를 안다
