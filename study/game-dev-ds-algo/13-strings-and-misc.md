## 1. 문자열 알고리즘

### Trie (접두사 트리)
- 닉네임/검색어 자동완성
- 개발자 콘솔 명령어 자동완성
- 커맨드 시퀀스 매칭

### Aho-Corasick — 금칙어 필터의 실전 해답
Trie에 **실패 링크**를 추가해, 수천 개의 금칙어를 **문장 한 번 스캔(O(문장 길이))** 으로 전부 검출합니다.

```
금칙어 3000개를 각각 Contains로 검사 → 3000 × 문장길이
Aho-Corasick                          → 문장길이 1회
```

### 실무에서 금칙어 필터가 어려운 이유
알고리즘보다 **우회 대응**이 본체입니다.
```
정규화 전처리:
  대소문자 통일 / 공백·특수문자 제거 / 유사 문자 치환 (0→o, 1→i, @→a)
  전각↔반각 변환 / 자모 분리 재조합 (한글) / 중복 문자 축약 (ㅋㅋㅋㅋ → ㅋ)
```
과도한 필터는 **오탐**(정상 단어가 걸림)을 만들어 UX를 해칩니다. 화이트리스트 병행이 필요합니다.

### 레벤슈타인 거리 (편집 거리)
- 검색 오타 보정 ("길드원 찾기"에서 한 글자 틀려도 검색됨)
- 유사 닉네임 탐지 (사칭 방지)
- DP로 O(nm), 임계값 이하만 필요하면 밴드 최적화

## 2. 문자열 → 정수 해시 인터닝

게임 루프에서 문자열 비교는 비쌉니다. **정수로 미리 바꿔둡니다.**

문자열 키의 비용이 왜 누적되는지(해시 계산 O(len) + 동등 비교 O(len), .NET은 해시를 캐시하지 않음)는
[02번 문서의 키 타입별 숨은 비용](02-hash-and-set.md#키-타입별-숨은-비용)에 정리해두었습니다.

```csharp
// 나쁨: 호출할 때마다 내부에서 문자열 → 정수 변환이 일어남
void Update() {
    animator.SetFloat("Speed", speed);
    mat.SetColor("_Color", c);
}

// 좋음: 변환을 시작할 때 1회만
static readonly int SpeedHash = Animator.StringToHash("Speed");
static readonly int ColorID   = Shader.PropertyToID("_Color");

void Update() {
    animator.SetFloat(SpeedHash, speed);     // 정수 그대로 전달
    mat.SetColor(ColorID, c);
}
```

> 문자열은 **사람이 읽기 위한 것**이고, 런타임 루프에는 정수만 흘러다니게 만드는 것이 인터닝의 요지입니다.

### 직접 쓰는 경우
FNV-1a나 xxHash로 에셋 경로·이벤트 이름을 정수 ID로 변환해 딕셔너리 키로 사용.
개발 빌드에서만 역매핑 테이블(`int → string`)을 유지해 로그/디버깅이 가능하게 합니다.

### 주의 — `string.GetHashCode()` 결과를 영속화하지 말 것

직접 ID를 만들려 할 때 흔히 하는 실수입니다.
```csharp
int id = "sword_iron".GetHashCode();   // 세이브 파일이나 패킷에 저장 ← 위험
```
.NET Core 계열은 해시 DoS 방지를 위해 **프로세스 실행마다 문자열 해시 시드가 달라집니다.**
같은 문자열이라도 게임을 재시작하면 값이 바뀔 수 있어, 세이브 파일이나 네트워크 프로토콜에 쓰면 다음 실행에서 깨집니다.

영속화가 필요하면 **직접 구현한 안정적인 해시**를 쓰세요.
```csharp
// FNV-1a — 실행 환경·런타임 버전과 무관하게 항상 같은 값
static uint Fnv1a(string s) {
    uint h = 2166136261;
    for (int i = 0; i < s.Length; i++) { h ^= s[i]; h *= 16777619; }
    return h;
}
```
`Animator.StringToHash`는 Unity 자체 알고리즘이라 런타임 내에서는 안정적이지만,
**엔진 버전 간 보장은 없으므로 영속 저장은 피하는 편이 안전**합니다.

> 해시를 ID로 쓸 때는 **충돌 검사**도 잊지 마세요. 32bit 해시에 키 7만 개면 생일 문제로 충돌 확률이 절반을 넘습니다.
> 빌드 시점에 전체 키를 해싱해 충돌이 없는지 검증하는 단계를 넣는 것이 일반적입니다.

## 3. 압축 · 직렬화

| 기법 | 사용처 |
|---|---|
| **비트 패킹** | 네트워크 패킷, 세이브 파일. 불리언 8개 = 1바이트 |
| **양자화** | float 위치를 16bit로, 각도를 8bit로 |
| **델타 인코딩** | 이전 값과의 차이만 저장. 리플레이, 스냅샷 |
| **RLE (Run-Length)** | 타일맵/복셀처럼 같은 값이 연속되는 데이터 |
| **허프만 / LZ4 / Zstd** | 에셋 번들, 세이브 파일. LZ4는 압축률보다 **해제 속도**가 좋아 런타임에 유리 |
| **팔레트화** | 복셀 청크의 블록 종류가 적으면 인덱스만 저장 |

### 세이브 파일 설계 포인트
- **버전 필드 필수** — 업데이트 후 구버전 세이브 마이그레이션
- 체크섬으로 변조/손상 탐지
- 쓰는 중 크래시 대비: 임시 파일에 쓰고 성공 시 rename (원자적 교체)

## 4. 게임 수학 — 알고리즘만큼 자주 쓰는 도구

### 내적 (Dot Product)
```csharp
Vector3.Dot(a, b) = |a||b|cosθ

// 시야각 판정
Vector3.Dot(forward, toTargetNormalized) > Mathf.Cos(halfFovRad)

// 앞/뒤 판정
Vector3.Dot(forward, toTarget) > 0   // 앞쪽

// 벽에 미끄러지는 이동 (투영 제거)
Vector3 slide = move - Vector3.Dot(move, normal) * normal;

// 반사 (튕기는 총알)
Vector3 reflect = dir - 2 * Vector3.Dot(dir, normal) * normal;
```

### 외적 (Cross Product)
```csharp
Vector3.Cross(a, b)   // a, b에 수직인 벡터

// 좌우 판정 (2D/평면)
float side = Vector3.Cross(forward, toTarget).y;   // >0 오른쪽, <0 왼쪽
// 삼각형 법선, 면적 계산에도 사용
```

### 쿼터니언
- **짐벌락**을 피하고 회전을 안정적으로 보간하기 위해 사용
- 오일러각은 **UI 표시와 기획 입력용**으로만, 내부 연산은 쿼터니언
- 보간은 `Slerp` (등속 회전), 짧은 각도면 `Lerp` + 정규화도 허용
- 회전 합성은 곱셈이며 **순서가 중요**: `qA * qB ≠ qB * qA`

### 변환 행렬
```
월드 행렬 = T(이동) × R(회전) × S(스케일)
자식 월드 = 부모 월드 × 자식 로컬
```
- 좌표계 변환: 로컬 ↔ 월드 ↔ 뷰 ↔ 클립 ↔ 스크린
- `transform.InverseTransformPoint`로 월드 좌표를 로컬로 (히트박스 판정에 유용)

### 자주 쓰는 도구
| 함수 | 용도 |
|---|---|
| `Mathf.Approximately` | 부동소수 비교 (`==` 금지) |
| `Mathf.DeltaAngle` | 각도 차이를 -180~180으로 정규화 |
| `Mathf.Repeat` / `PingPong` | 순환 애니메이션 |
| `Vector3.ProjectOnPlane` | 경사면 이동 |
| `Quaternion.LookRotation` | 특정 방향 바라보기 |
| `Mathf.SmoothDamp` | 스프링식 부드러운 추적 (카메라) |

## 5. 결정론 (Determinism)

롤백 넷코드·락스텝·리플레이·버그 재현에 필수입니다.

### 결정론을 깨는 것들
| 원인 | 대응 |
|---|---|
| **부동소수점 플랫폼 차이** | 고정소수점(Q16.16) 또는 소프트웨어 수학 라이브러리 |
| `Time.deltaTime` 가변 | **고정 타임스텝** 시뮬레이션 |
| `UnityEngine.Random` 전역 상태 | 시드 기반 독립 RNG 인스턴스 |
| `Dictionary`/`HashSet` 순회 순서 | 정렬된 컨테이너 또는 배열 사용 |
| 객체 참조 주소 기반 정렬/해시 | 안정적인 ID 부여 |
| 물리 엔진 내부 비결정성 | 자체 결정론 물리 또는 결정론 지원 엔진 |
| 멀티스레드 처리 순서 | 결정론적 작업 분할과 병합 |

### 검증 방법
매 N프레임 전체 상태의 **체크섬**을 계산해 비교. 어긋나는 순간의 프레임과 엔티티를 기록하면 데스싱크 디버깅이 가능해집니다.

## 6. 기타 알아두면 좋은 것들

| 기법 | 설명 |
|---|---|
| **블룸 필터** | "확실히 없음"을 싸게 판정. 중복 체크 사전 필터, 청크 로드 여부 캐시 |
| **LRU 캐시** | 에셋/청크 캐시 관리. 딕셔너리 + 이중 연결 리스트 |
| **Zobrist 해싱** | 보드 게임 국면을 정수 해시로. 트랜스포지션 테이블 |
| **빈 패킹** | 텍스처 아틀라스, 라이트맵 UV 배치 |
| **Marching Squares** | 격자 → 부드러운 윤곽선 (08번 문서) |
| **Voronoi 다이어그램** | 영역 분할, 바이옴 경계, 도시 구역 생성 |
| **들로네 삼각분할** | 점 집합의 자연스러운 연결. 던전 방 연결(04번 문서), 지형 메시 |
| **커맨드 패턴** | Undo/Redo, 리플레이, 입력 기록, AI 행동 큐 |
| **상태 스냅샷 직렬화** | 롤백, 세이브, 리플레이의 공통 기반 |
