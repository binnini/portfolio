엔진 비의존 코어와 Unity 어댑터 분리

Assembly Definition · 의존성 역전

전투·맵·카드 규칙을 UnityEngine을 참조할 수 없는 어셈블리로 떼어내고, 그 경계를 컴파일러가 강제하게 했습니다.

문제

규칙이 MonoBehaviour 안에 있으면 “공격 카드가 맞게 처리되는가”를 확인하려고 매번 Unity를 켜고 Play를 눌러야 합니다. 턴제 게임은 규칙이 계속 바뀌는데, 손으로 플레이해서 확인하는 방식으로는 A를 고쳤더니 B가 깨진 것을 잡을 수 없습니다.

접근
  • 의존 방향을 표현 → 런타임 단방향으로 고정
  • 순수 계층 3개에 noEngineReferences: true — using UnityEngine이 컴파일 에러
  • 표현 계층이 전투 상태를 읽어야 하는 자리는 역참조 대신 seam으로 해결

축좌표 기반 육각 그리드와 경로 탐색

3D 수학 · 순수 C#

육각 격자를 3차원 큐브 좌표의 대각 평면으로 다뤄, 거리·회전·방향 판정에서 행 홀짝 분기를 완전히 없앴습니다.

문제

육각 격자는 이웃이 6개인데 행마다 반 칸씩 어긋납니다. (행, 열)로 저장하면 짝수 행과 홀수 행의 이웃 계산식이 서로 달라지고, 거리 계산은 더 복잡해집니다.

접근

축을 3개 두고 q + r + s = 0 제약을 겁니다. 저장은 q, r 두 개만 하고 s는 파생시켜 불일치를 원천 차단했습니다.

// 저장은 2개, 사용은 3축. S는 제약에서 유도된다.
public int S => -Q - R;

// 거리 — 한 칸 이동 시 합이 0이어야 하므로
// 항상 두 축이 ±1씩 변한다. 그래서 2로 나눈다.
public int DistanceTo(HexCoord o)
    => (Abs(Q-o.Q) + Abs(R-o.R) + Abs(S-o.S)) / 2;

// 60도 회전 = 좌표 순환 한 번. 삼각함수 불필요.
// 공격 패턴을 6방향으로 돌릴 때 사용.
var nextQ = -r;
var nextR = q + r;

// 방향 판정 — 큐브 공간 내적 최댓값.
// 동점은 enum 순서로 깬다(결정성 확보).
var dot = dq*d.Q + dr*d.R + ds*(-d.Q-d.R);
경로 탐색 — HexPathfinder
  • 지형별 BaseMoveCost가 달라 단순 BFS가 아닌 가중 최단경로
  • GetReachableCells(범위 하이라이트)와 FindPath(실제 경로)가 같은 계산을 공유해 규칙이 어긋날 수 없음
  • 맵·런타임 점유·지형 특성을 전부 인자로 주입 — 숨은 상태가 없어 어떤 상황도 테스트 가능
확장 사례 · 멀티셀 보스의 통과 판정
여러 칸을 차지하는 보스가 자기가 지나갈 수 없는 틈으로 걸어 들어가는 문제가 있었습니다. 처음에는 보스 이동을 아예 막아뒀다가, MovementQuery.FootprintRadius를 더해 “중심 칸 하나”가 아니라 중심 기준 반경 R 원판 전체가 통과 가능한지를 묻도록 바꿨습니다. 기본값 0이면 기존 동작 그대로라 기존 호출부를 한 곳도 고치지 않았고, 자기 몸이 이미 깔고 있는 칸은 점유 판정이 OccupyingUnitId != UnitId인 덕분에 예외 처리 없이 자동으로 통과합니다.
결과 — 좌표계를 바꾸자 거리·회전·방향이 각각 한 줄로 정리됐고, 이동·시야·공격 패턴이 모두 같은 좌표 연산 위에서 돌아갑니다. 전부 Map.Runtime(순수 C#)에 있어 씬 없이 검증됩니다.

턴 상태 머신과 “지켜지는” 적 행동 예고

상태 머신 · 계약 설계

적이 다음 턴 행동을 미리 보여주는 게임에서 생명은 “예고가 반드시 지켜진다”는 신뢰입니다. 그 신뢰를 규율이 아니라 자료구조로 강제했습니다.

페이즈 순환
PlayerMovement  ─EndAction()→
MonsterMovement ─Resolve→
PlayerAction    ─EndAction()→
MonsterAction   ─Resolve→  (다음 턴)

이동만으로는 페이즈가 전환되지 않습니다. EndAction()이 유일한 전환 트리거입니다. 전환 경로가 여러 개면 조합이 폭발하고 그중 하나의 이상 상태를 놓치게 되는데, 입구를 하나로 두면 “왜 넘어갔지?”의 답이 항상 하나입니다.

예고를 지키게 만든 세 장치
  • 커밋 시점 좌표 보존 — EnemyIntent.EnemyCoord는 라이브 좌표가 아니라 예고를 만든 시점의 좌표를 복사해 얼려둡니다. 몬스터가 움직여도 예고가 따라가지 않습니다.
  • 전 구간 잠금 — 커밋된 인텐트는 플레이어의 이동·액션·턴 종료 전 구간에서 유지됩니다. 플레이어가 움직였다고 다시 조준하지 않습니다.
  • 회피의 정의를 좁힘 — 공격 범위를 규칙이 아니라 구체적인 칸의 집합으로 확정해 보여줍니다. 집합 밖으로 나가야 회피이고, 안에서의 재배치는 회피가 아닙니다.
플랜 예약 — 프리뷰가 곧 플랜

몬스터 둘에게 각각 “가장 가까운 칸으로”라고 하면 둘 다 같은 칸을 고르고 해석 단계에서 하나가 밀려납니다. 그러면 예고와 결과가 달라집니다.

계획 시점에 목적지를 예약해 서로 겹치지 않게 했습니다. 예고를 만드는 계산과 실제 이동을 해석하는 계산이 같은 결과를 내도록 보장합니다.

순서가 곧 게임 규칙이다
턴 시작 시퀀스를 계약으로 고정했습니다 — ① 블록(방어도) 해제 → ② 필드 오브젝트 틱 → ③ 지속 효과 → ④ 예산·시야·인텐트 갱신 → ⑤ 페이즈 진입. 따라서 필드 피해는 블록이 해제된 뒤에 들어옵니다. ①과 ②를 뒤집으면 “방어도를 쌓아두면 다음 턴 장판을 막을 수 있는” 완전히 다른 게임이 되기 때문에, 문서로 고정하고 테스트로 잠갔습니다.
결과 — 페이즈 순환·인텐트 커밋·회피 판정·목적지 예약이 모두 EditMode 테스트로 잠겨 있어, 새 카드나 상태이상을 추가해도 “예고 = 실제 결과”가 깨지면 즉시 빨간불이 켜집니다.

암시야 — 렌더링이 아니라 정보 은닉 계층

데이터 경계 설계 · 셰이더

안개를 “안 보이는 칸을 검게 칠하는 일”이 아니라 “렌더러가 원본 데이터를 아예 받지 못하게 하는 일”로 설계했습니다.

문제

“검게 칠하기”로 만들면 렌더러는 원본 데이터를 전부 들고 있으면서 화면에만 안 그립니다. 그러면 툴팁이 안개 속 칸 이름을 띄우고, 미니맵이 아직 못 본 랜드마크를 표시하고, 새 UI를 만든 사람이 필터를 빠뜨립니다. 표면이 늘 때마다 누출 가능성이 생깁니다.

단계별 노출 경계
노출 항목HintedRevealed
지형 · 이동비용 · 보행 · 높이○○
타일 정의 · 이벤트 · 랜드마크✕○

Hinted는 “지나갈 수 있는 땅인가”까지만 답하고 “거기 무엇이 있는지”는 숨깁니다. 플레이 경험으로는 “길이 있는 건 알겠는데 뭐가 있는진 모르겠다”가 됩니다.

해결 — 걸러진 뷰만 건넨다
// HexVisibilityRuntime.GetSafeCellInfo
if (visibility == Unknown)
    return SafeCellInfo.Unknown(coord);   // 아무것도 안 줌

if (visibility == Hinted)
    return new HexVisibilitySafeCellInfo(
        coord, visibility, true, true, false,
        string.Empty,        // 타일 정의 id  숨김
        cell.TerrainTypeId,  // 지형        노출
        cell.BaseMoveCost,   // 이동 비용    노출
        cell.BaseWalkable,   // 보행 가능    노출
        cell.BaseBlocksVision,
        string.Empty,        // 이벤트 id    숨김
        string.Empty,        // 랜드마크 id  숨김
        cell.VisualFloor, isTrapRevealed);

return new HexVisibilitySafeCellInfo( /* 전부 노출 */ );

원본 cell은 이 함수 밖으로 나가지 않습니다. 나가는 것은 단계에 따라 걸러진 별도 구조체뿐이라 소비자가 필터를 우회할 방법이 아예 없습니다. 새 UI를 만드는 사람이 실수하려야 할 수가 없습니다.

대표 사례 — 증분 시야 갱신

다만 카운터와 청크 멤버십은 일부러 전 셀에 대해 계속 계산합니다(저렴하므로). 공개 계약을 바꾸지 않기 위해서입니다 — 빨라졌지만 겉보기 결과는 완전히 동일합니다.

되돌린 최적화

무엇을 게이트로 삼을 것인가

프레임 시간은 기계마다 다릅니다. 이걸 게이트로 쓰면 코드가 멀쩡한데 빨간불이 뜨고, 곧 사람들이 그 테스트를 무시하기 시작합니다. 무시당하는 게이트는 없는 것보다 나쁩니다.

MapCombatController.cs가 10,690줄 단일 클래스까지 커졌습니다 (멤버 선언 766건, [SerializeField] 148건). 1개월 공모전 일정에서 기능을 우선했던 결과이고, 개발이 이어지면서 갚기 시작했습니다.

  • 멤버 766건을 어느 seam에 속하는지 분류표부터 만들고 시작
  • 가장 작은 seam(ICombatAudioHost, 멤버 6개)부터 단계별로
  • 껍데기는 남기고 속만 옮기는 strangler 방식
Unity라서 지켜야 했던 제약

씬과 프리팹은 코드를 문자열·GUID로 참조합니다. 이름을 바꾸면 컴파일은 되는데 실행하면 null이 됩니다.

테스트가 이미 빨간불이었을 때

리팩토링 시작 시점의 EditMode 베이스라인은 117개 실패 상태였습니다. “전부 초록으로 만들고 시작”은 현실적으로 영원히 시작하지 못한다는 뜻이라, 게이트를 “신규 실패 0”으로 정의하고 단계마다 실패 집합이 늘지 않았음을 확인하며 전진했습니다.

씬 수술 — 재발 방지가 본체다
타일을 클릭하려고 콜라이더를 타일마다 붙여 두었더니 MainGameplay 씬에 클릭 콜라이더 139,146개가 구워져 씬 파일이 317 MB, 로드가 17.5초까지 갔습니다. 콜라이더 대신 스크린 좌표를 헥스 좌표로 직접 변환하는 방식(TryScreenToHex)으로 바꾸고 구워진 오브젝트를 전부 삭제해 50 MB · 0.56초가 됐습니다. 중요한 건 그다음입니다 — 골든 베이스라인에 clickColliders: 0을 잠가 콜라이더 생성 경로가 되살아나면 게이트가 실패하게 했고, 실제 씬·실제 카메라로 좌표 변환을 왕복 검증하는 테스트를 함께 넣었습니다.
결과 — 본체 10,690줄 → 2,233줄 + 관심사별 분할, 오디오·카메라는 별도 클래스로 추출. 베이스라인은 117 실패에서 925 pass / 0 fail로 초록이 됐습니다. 다만 CombatState.cs는 아직 6,907줄로 남아 있어 분해가 진행 중입니다.

일하는 방식

기록으로 남기고 강제한다

3인 팀에서 개발을 혼자 맡았고 기획이 계속 바뀌었습니다. “저번에 왜 이렇게 정했더라”를 반복하지 않으려고 결정을 배경·대안과 함께 기록하기 시작했고, 시스템 스펙의 각 조항에 담당 테스트를 붙여 문서와 코드가 어긋나면 테스트가 깨지도록 했습니다.

AI 도구를 쓰는 관점

AI 활용의 한계는 도구가 아니라 코드베이스 구조가 정한다고 봤습니다. 게임 규칙을 순수 C#으로 분리해 CLI에서 테스트가 도는 영역을 만들자, 에이전트가 고치고 → 돌리고 → 다시 고치는 검증 루프를 스스로 닫을 수 있게 됐습니다. 규칙은 프롬프트로 지시하는 대신 asmdef 제약으로 컴파일러가 강제하게 했습니다.

덜어낸 판단도 기록했다
  • 시야 차폐(line-of-sight)는 구현하지 않기로 결정하고 테스트로 잠갔습니다 — 시야는 순수 거리라는 계약을 고정
  • 어셈블리를 더 잘게 쪼갤지 검토했다가 분리하지 않기로 종결
  • Mesh 재사용 풀은 넣었다가 효과가 없어 되돌렸습니다

공모전 1개월 구간에는 기능을 우선해서 밀었고, 개발이 계속 이어지게 되자 계측하고 분해하고 테스트를 채웠습니다. 급할 땐 빠르게 밀고, 오래 갈 프로젝트가 되면 갚는다는 기준으로 판단했습니다.

앞으로 — 기억결은 지금도 개발 중이고 2026 GES 전시를 준비하고 있습니다. 남은 과제도 알고 있습니다. 측정이 아직 에디터 플레이 모드에 머물러 있어 실기기 프로파일링이 필요하고, CombatState 분해와 Addressables 기반 리소스 관리는 아직 손대지 못했습니다. 다음에 배우고 싶은 것도 그쪽입니다.
