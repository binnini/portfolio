인게임 플로우

한 턴의 진행 순서

게임은 턴제 방식으로 진행되며 한 턴은 플레이어 이동 → 몬스터 이동 → 플레이어 액션 → 몬스터 액션 네 페이즈로 돌아갑니다. 이동과 액션이 나뉘어 있어, 먼저 자리를 잡고 나서 무엇을 할지 고르는 순서가 됩니다. 기력이라는 공유 자원으로 이동과 액션(공격 · 방어)을 분배하기 때문에, 플레이어는 이동과 액션을 잘 분배하며 탐험과 전투를 진행합니다.

현재 구현 범위 — 카드 60종 · 몬스터 6종 · 레벨 2개(튜토리얼 맵, 스테이지 맵)

도메인 코어와 어댑터 분리 (Ports & Adapters)

헥사고날 · Observer · asmdef 경계
문제
  • ① 초기에는 게임 로직이 Unity Engine에 종속되어, 로직을 추가하거나 변경할 때마다 Play 모드에 진입해 테스트해야 했고 해당 시간이 개발 속도를 늦췄습니다.
  • ② AI 에이전트를 개발에 투입하면서 테스트 단계에서 사람이 병목이 됐습니다. 로직의 작성 속도를 사람이 따라가기 벅찼고, 규모가 커질수록 작성한 기능의 테스트가 자꾸 미뤄지는 문제가 발생했습니다.
  • ③ 초기에는 하나의 MonoBehaviour 파일에 모든 게임 로직을 작성했고, 그 결과 한 파일이 10,690줄까지 커졌습니다.
선택한 구조
  • 도메인 코어 / 어댑터 분리 — Ports & Adapters(헥사고날)
    전투 · 맵 · 카드 로직을 UnityEngine 비의존 어셈블리로 떼어내, Play 모드 없이 EditMode와 CLI 환경에서 테스트를 검증할 수 있도록 했습니다. → ① ②
  • 결과 이벤트 발행 — Observer
    도메인은 결과만 이벤트로 올리고 화면 · 소리 · 카메라가 각자 구독하도록 하여, 이후 연출을 늘려도 도메인 코드가 커지지 않게 했습니다. → ③
  • asmdef 참조 제약
    어댑터 → 코어 단방향만 허용하여 빌드를 막는 조건을 두었습니다.
효과
얻은 것근거
① Play 모드 없이 게임 로직 검증 씬 로드와 Play 모드 진입 없이 에디터에서 바로 실행되는 EditMode 테스트 925건. 로직 변경 후 확인까지 초 단위
② AI 에이전트가 검증까지 스스로 수행 도메인이 UnityEngine 비의존이라 CLI 테스트 환경 조성
③ 연출과 게임 로직 파일의 비의존성 확보 이펙트 · 효과음 · 화면 흔들림 · 카메라 연출을 Presenter와 CSV 기반 큐 테이블에서 추가

데이터 중심 구조 — CSV와 ScriptableObject

에디터 임포터 · 임포트 시점 검증 · 전략 패턴
문제
  • ① 공모전 1차 심사를 위해 한 달이라는 한정된 기간 안에 제작해야 했고, 제작 도중 기획을 수정하는 일이 많았습니다. 단순 serialized field로 데이터를 관리해서는 제작 속도 · 협업 · 밸런싱에 어려움이 있었습니다.
  • ② ‘카드 게임’이라는 특성상 데이터가 많고 효과가 다양해 관리가 어려웠습니다. 또한 카드에 따라 다양한 규칙이 존재하는데, 별도의 검증 루프가 없어 오류가 자주 발생했습니다.
해결 방안
  • CSV 저작 → 에디터 임포터 → ScriptableObject
    수치 · 사거리 · 코스트 · 희귀도까지 전부 컬럼으로 옮겨, 인스펙터를 거치지 않고 표 한 장에서 밸런싱합니다. → ①
  • 효과 디스패처 (전략 패턴)
    공통 카드는 공통 경로로 처리하고, 규칙이 다른 카드만 전용 핸들러에 위임해 카드가 늘어도 분기가 늘지 않게 했습니다. → ②
  • 임포트 시점 검증
    잘못된 값을 관대하게 넘기지 않고 임포트를 실패시켜, 게임을 켜기 전에 검증 루프가 돌게 했습니다. → ②
효과 디스패처 — 특수 카드만 핸들러를 가진다
// Combat/Runtime/CombatState.CardEffects.cs
defendHandlers =
  ToEffectRefMap<IDefendEffectHandler>(new[] {
    new ZeroThenDoubleDefendEffectHandler(),
    new HalfReflectDefendEffectHandler(),
    new CleanseBlockDefendEffectHandler(), ...
  });

카드 종류는 이동 · 방어 · 유틸 · 정찰 · 공격 · 필드 6가지 타입으로 나뉘어 있고, 이와 별개로 특수 카드 핸들러 24종을 구현했습니다.

일반 카드는 타입별 공통 경로를 그대로 타고, 규칙이 다른 카드만 effectRef로 자기 핸들러를 찾아갑니다.

효과
① 밸런스 조정에 빌드 불필요 데이터 수정 시 CSV 행을 고치고 임포트하여 반영. 기획 담당 팀원이 수치와 설명 문구를 직접 수정
② 카드 추가가 기존 카드에 영향 없음 기존에 없던 규칙일 때만 핸들러를 하나 추가하고 화이트리스트에 등록
② 잘못된 데이터가 게임에 도달하지 않음 임포트가 먼저 실패. 규칙 자체도 임포터 테스트가 검증
적용 범위 — 카드 · 몬스터 · 공격 패턴 · 보스 페이즈 · 상태이상 · 유물 · 소모품 · 상점가 · 보상 · VFX · 사운드 · 공격 타이밍까지 CSV 원본 27개가 같은 파이프라인을 씁니다.

Unity Profiler 기반 성능 최적화 (1)

진단 과정 · CASE 1 · CASE 2

공모전 일정에 맞춰 기능을 우선하여 프로토타입을 제작한 후, 성능 최적화를 진행하였습니다. 그 당시 턴이 전환될 때마다 눈에 띄는 속도 저하가 있었고, 이를 해결하기 위해 여러 진단과 테스트를 진행했습니다.

진단과 테스트
① 턴 전환 구간 측정
steady    :  8.8 ms   draw call 205
move_turn : 56.0 ms   draw call 210
→ 그릴 양은 그대로, 시간만 6배

② ProfilerMarker 로그
[턴 전환 기준]
  Vis.ApplyVisibility   59.0 ms ← 암시야 처리
  Vis.OverlayApply        1.2 ms
  Pathfind                4.8 ms
[이동 1회 기준]
  Vis.OverlayBuild      10.4 ms ← 몬스터 예고
  • ① GPU vs CPU — 가장 먼저 Profiler로 턴이 전환되는 타이밍의 드로우콜과 지연 시간을 측정했습니다. 드로우콜은 큰 변화가 없었으나 지연 시간만 8.8 → 56.0 ms 수준으로 폭발하는 것을 확인했고, CPU의 턴 처리 코드가 원인이라고 파악했습니다.
  • ② 어느 함수인가 — 턴 처리 경로에 지연 시간을 기록하는 ProfilerMarker를 제작했습니다. 로그를 확인한 결과 암시야 처리 로직과 몬스터 예고 오버레이 두 곳이 원인임을 확인했습니다.
CASE 1 시야 갱신 더티 플래그 · 증분 갱신 O(n) → O(k) 59 → 5.8 ms/turn
초기 구현

시야가 바뀌면 맵 전체의 안개 청크 메시를 파괴하고 다시 생성했습니다. 스테이지 한 판의 타일이 약 4,500칸인데, 몇 칸이 바뀌었든 항상 전체를 훑습니다. 게다가 이 갱신이 턴당 두 번 돌고 있었습니다.

측정

Vis.ApplyVisibility
59 ms/turn

턴 전환 지연의 대부분

조치

칸별 (Exists, Visibility)를 기억해 두고 직전과 달라진 칸만 재적용합니다. 안개 메시도 미탐색·탐색 칸 집합이 실제로 바뀌었을 때만 재생성합니다.

여기에 버전 스탬프를 얹어, 호출자가 “바뀐 것 없음”을 알리면 맵 전체 재스캔을 통째로 건너뜁니다. 선택만 바꾸는 갱신은 바뀐 칸이 0이므로 낭비되던 두 번째 패스가 함께 사라졌습니다.

한 번 이동에 실제로 달라지는 칸은 시야 경계 부근 수십 칸입니다. 전체 칸 n을 매번 훑던 작업이 바뀐 칸 k에 비례하도록 바뀌었습니다.

CASE 2 몬스터 예고 오버레이 메모이제이션 · 해시 무효화 O(m) → O(1) 10.4 → 2.1 ms/move
초기 구현

몬스터의 이동 예고 · 공격 범위 · 추격 표시를 화면을 갱신할 때마다 처음부터 다시 계산했습니다. 같은 상황에서 같은 결과를 반복해 만들고 있었습니다.

측정

Vis.OverlayBuild
10.4 ms/move

한 칸 이동할 때마다 지불하는 비용

조치

흩어져 있던 계산을 하나로 합치고, 결과를 캐시했습니다. 다시 계산하는 조건은 “상황이 실제로 바뀌었는가” 하나입니다.

여기서 ‘상황’은 몬스터 위치 · 예측 이동 · 공격 패턴 · 플레이어 위치 · 가시성을 하나의 해시 값으로 압축한 것입니다. 이전 해시와 같으면 계산을 건너뛰고 이전 결과를 그대로 씁니다.

CASE 3 · CASE 4 · 결과
재측정 — CASE 2까지 적용한 뒤, 정본 씬의 암시야 표현을 오버레이 틴트에서 조명 마스크 모드로 전환했습니다. 그러자 시야 갱신 비용이 다시 올라갔고, 마커를 따라가 원인을 좁혔습니다.
CASE 3 조명 마스크 재빌드 좌표 변환 메모이제이션 O(R·n) → O(n) 1.97 → 0.18 ms/frame
초기 구현

조명 마스크 방식 — 맵 위에 검은 밝기 텍스처를 한 장 얹고, 셰이더가 타일을 그릴 때 자기 위치의 픽셀을 읽어 색에 곱합니다. 픽셀이 검으면 그 타일은 어둡게 보입니다. 크기는 128×128 = 픽셀 16,384개입니다.

시야는 한 칸 움직일 때마다 바뀌므로, 이동할 때마다 픽셀 16,384개를 다시 채웁니다.

for i in 0..16383:
  칸 = WorldToCoord(i)
  pixels[i] = 밝기[칸]

WorldToCoord를 매번 다시 계산합니다.

측정

Atlas.Vis.LightingMask
1.97 ms/frame

60fps 예산 16.7 ms의 약 12%를 마스크 재빌드 하나가 쓰고 있었습니다.

조치

WorldToCoord를 메모이제이션했습니다. “픽셀 i는 어느 칸인가”의 답은 맵과 텍스처 크기가 고정이라 게임 내내 같은 값입니다. 매번 바뀌는 것은 그 칸의 밝기뿐입니다.

// 1회만 계산해 배열에 저장
칸번호[i] = WorldToCoord(i)

// 이동할 때마다
pixels[i] = 밝기[칸번호[i]]

좌표 변환 횟수가 이동할 때마다 16,384회에서 게임 전체 통틀어 16,384회로 바뀝니다. 재빌드에 남는 것은 배열 조회뿐입니다.

계산 결과를 바꾼 게 아니라 계산 시점을 앞으로 옮긴 것이라 출력 픽셀이 이전과 동일합니다.

별개 증상 — 위 셋은 전부 프레임 시간이었습니다. CASE 4는 플레이 시작 전 대기로 관찰돼, 프레임 마커가 아니라 씬 파일 크기와 로드 시간을 직접 재는 것에서 출발했습니다.
CASE 4 씬 로드 직렬화 데이터 감축 Raycast → O(1) 역산 17.5초 → 0.56초
초기 구현

타일 클릭을 받으려고 타일마다 콜라이더를 붙이고, 마우스 위치에서 Raycast를 쏴 어떤 타일에 맞았는지 판정했습니다. 가장 단순하고 확실한 방법이었지만, 타일과 그 측면마다 콜라이더가 붙어 맵 하나에 클릭 콜라이더 139,146개가 씬 파일에 그대로 구워졌습니다.

측정

씬 파일 317 MB
로드 17,480 ms

플레이를 눌러도 17.5초 동안 아무것도 시작되지 않는 상태

조치

콜라이더와 Raycast를 걷어내고, 스크린 좌표를 헥스 좌표로 직접 역산해 클릭을 판정하도록 바꿨습니다. 물리 표면 없이 순수 계산으로 처리됩니다. 씬은 50 MB가 됐습니다.

턴당 프레임 비용 (move_turn, ms) — 60fps 예산 16.7 ms

Rainbow War — 영역 확장·침탈 알고리즘

폴리곤 기하 · 런타임 메시

영역은 플레이어가 궤적을 완성할 때마다 갱신됩니다. 이때 자신의 영역이 넓어지는 확장과 상대방의 영역을 제거하는 침탈 두 가지 효과가 일어납니다. 여기서 ① 확장 시 어느 갈래를 남길지, ② 침탈 결과가 여러 조각으로 갈라지는 것 둘을 풀어야 했습니다.

① 확장 둘레 두 갈래 중 어느 쪽을 남길 것인가 폴리곤 합집합 연산 없음

궤적이 영역을 떠난 A와 되돌아온 B가 기존 폴리곤 둘레를 두 갈래로 나눕니다. 양 끝점을 가장 가까운 정점에 스냅한 뒤, 각 갈래에 궤적을 이어 붙여 조각 2개를 만듭니다.

두 조각 중 넓은 쪽이 곧 ‘기존 영역 + 새로 감싼 땅’입니다. 궤적은 영역 밖에 있을 때만 기록되므로, 새로 감싼 땅은 기존 영역과 겹치지 않습니다. 그래서 두 폴리곤을 합치는 기하 연산 없이 넓이만 비교해 확장을 끝냅니다.

// Trail_Action.ExpandArea
TrailArea.TryCut(areaPieces[i], trail,
                 out a, out b);
areaPieces[i] = GetPolygonArea(a)
             >= GetPolygonArea(b) ? a : b;
② 침탈 영역이 상대에 의해 잘리면, 잘린 만큼 복수의 폴리곤으로 나눈다

상대 영역을 가로질러 지나가면 그 영역이 내 궤적을 경계로 잘립니다. 가져오는 것은 내가 감싼 쪽이고, 그 조각은 좁을 수도 넓을 수도 있습니다. ①의 넓이 규칙은 여기서 쓸 수 없습니다.

한 궤적이 상대 영역을 여러 번 드나들면 상대에게는 조각 여러 개가 남습니다. 그래서 영역을 폴리곤 하나가 아니라 List<List<Vector3>> 조각 목록으로 표현합니다.

foreach (var cut in cuts)      // 다 자르고
    pieces = CutAll(pieces, cut);  // 둘 다 보관
foreach (var p in pieces)     // 판정은 마지막에
    if (!IsTakenBy(p, this, cutPoints))
        survived.Add(p);

자를 때는 어느 쪽도 버리지 않고, 전부 자른 뒤 조각마다 소유권을 한 번씩 판정합니다.

출처 표기 — 포함 판정(Ray casting) · 넓이(Shoelace) · 삼각분할(Ear clipping)은 공개 구현을 가져다 쓰고 코드 주석에 출처를 남겼습니다. 제가 설계한 것은 이를 조합한 영역 표현과 확장 · 침탈 규칙입니다.

폴리곤 절단은 무거운 연산이라 매 프레임 스트리밍할 수 없습니다. 소유 클라이언트에서만 계산하고, 확정된 정점 배열만 폐쇄 · 침탈 시점에 보냅니다.

겪은 문제와 해결
① 클라이언트마다 시작 시점이 어긋난다

문제 — 기기와 회선 차이로 씬 로딩 완료 시각이 다릅니다. 각자 타이머를 돌리면 60초 제한 시간이 서로 다른 시점에 끝나 승패 판정이 어긋납니다.

해결 — 마스터가 서버 시계의 원점을 룸 프로퍼티에 기록하고 나머지가 그 값을 읽어 같은 경과 시간을 계산합니다. RPC와 달리 룸 프로퍼티는 상태로 남아 늦게 읽어도 유효합니다. 여기에 오브젝트 생성 완료 배리어를 더해 초기화 순서도 보장했습니다.

② 늦게 들어온 클라이언트가 남의 영역을 모른다

문제 — 영역은 변경 시점에만 브로드캐스트되므로, 나중에 들어온 클라이언트는 그 전의 이벤트를 전부 놓칩니다.

해결 — 진입한 쪽이 기존 참가자에게 최신 영역을 역요청(pull)하도록 했습니다. OthersBuffered로 push하면 게임 내내 모든 변경 이력이 버퍼에 쌓입니다.

지금이라면 고칠 것 — 점수판을 Update에서 매 프레임 전 클라이언트에 RPC로 보내고 있습니다 (당시에도 비효율을 알고 코드에 TODO를 남겨뒀습니다). 영역도 조각 전체를 보내므로 정점 수에 비례해 페이로드가 늘어납니다. 당시에는 전송량과 프레임 시간을 측정하지 않았습니다.
